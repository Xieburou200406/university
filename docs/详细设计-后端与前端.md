# 详细设计文档 — 波动率交易决策辅助系统（正式版）

> 配套文档：`../AGENTS.md`（铁律与里程碑）、`./波动率决策辅助系统-架构设计与Agent文档.md`（需求与 Agent 分工）。
> 本文档回答六个问题：**用什么架构、后端选什么工具、类怎么设计、数据库怎么建、API 长什么样、前端怎么设计**。
> 设计原则：铁律不靠自觉，靠结构强制（见 §10 对照表）。

## 0. 设计约束（先看清再设计）

| 约束 | 取值 | 对设计的影响 |
|---|---|---|
| 频率 | 日频（T 日收盘后跑一次） | 无并发压力，不需要异步全家桶/Celery |
| 用户 | 单人~小团队，非对称信任（自己用） | 鉴权从简（API Key），不上 JWT/RBAC |
| 合规 | 只建议不下单 | 后端**永远没有**下单模块，前端没有"执行"按钮 |
| 部署 | Windows 本机为主，可迁云 | 所有组件可用 `uvicorn + schtasks` 起步，容器化留接口 |
| 现有资产 | 领域逻辑已在 demo 验证（SVI R²=0.99、归因残差 4%） | 重构是"搬家"不是"重写"，迁移前后数字必须复现 |
| 生态 | 散户金融图表、中国习惯 | 图表库必须有红涨绿跌和 K 线生态 |

## 1. 总体架构

```
┌─────────────────────────────────────────────────────────────────┐
│  前端 SPA (Vue3 + ECharts)          静态产物由后端托管            │
│  Dashboard / 信号台 / 风控台 / 归因 / 回测 / 持仓管理              │
└───────────────▲─────────────────────────────────────────────────┘
                │ REST (JSON) + OpenAPI 类型
┌───────────────┴─────────────────────────────────────────────────┐
│  API 层  FastAPI (薄壳，无业务逻辑)                                │
│  routers: market / signals / positions / risk / backtest / jobs  │
│  schemas: Pydantic v2 —— 量纲校验在这里发生（第一道防呆）           │
├─────────────────────────────────────────────────────────────────┤
│  领域包 vol.*（纯 Python，不 import 任何 web 框架）                 │
│  data → pricing → signals → risk → portfolio → backtest → report │
├─────────────────────────────────────────────────────────────────┤
│  持久层  SQLite (SQLAlchemy 2.x + Alembic)  +  CSV/Parquet 缓存    │
└─────────────────────────────────────────────────────────────────┘
      ▲                                    ▲
      │ 每日 15:35 定时触发                  │ 手动"刷新数据"按钮
┌─────┴────────────┐            ┌──────────┴──────────┐
│ scheduler 进程    │            │ POST /api/jobs/refresh│
│ APScheduler cron │───同一管线──▶│ (带锁，防重入)         │
└──────────────────┘            └─────────────────────┘
        每日管线 pipeline.run(): 拉数→缓存→定价→信号→风控→建议卡→落库
```

**三个进程形态**（可同机共存）：

1. `uvicorn api.main:app` — API + 静态前端，端口 8000；
2. `python -m jobs.scheduler` — APScheduler 独立进程，日频触发管线；
3. 前端 build 产物放 `backend/static/`，由 FastAPI `StaticFiles` 托管——**单端口交付**，浏览器只开 `http://localhost:8000`。

**分层纪律**（继承 demo，写进 CI 检查）：
- `vol.*` 不 import fastapi/uvicorn（领域层可独立测试、可被任何壳复用）；
- `api/` 不写计算逻辑，只做参数校验 + 调领域包 + 序列化；
- 只有 `vol.data` 允许 import akshare / requests（联网点唯一）。

## 2. 技术选型与论证

### 2.1 后端：**FastAPI**（不选 Django 的理由也要写清）

| 维度 | FastAPI + SQLAlchemy | Django + DRF | Flask | 维持 Streamlit |
|---|---|---|---|---|
| 包裹现有纯函数计算层 | ★★★ 直接包函数 | ★★ 需套 app/views 惯例 | ★★★ | —（面板即代码，无 API） |
| 类型/量纲防呆 | ★★★ Pydantic v2 原生 | ★★ serializer 较弱 | ★ 靠手写 | 无 |
| API 文档/前端对接 | ★★★ 自动 OpenAPI→TS 类型 | ★★★ DRF Schema | ★★ | 无 API |
| ORM/迁移 | ★★ SQLAlchemy2+Alembic | ★★★ 自带，最省心 | ★★ | 无 |
| Admin 后台 | 无（可用 sqladmin 补） | ★★★ 免费 | 无 | — |
| 调度集成 | ★★★ APScheduler 同进程 | ★★ 需 Celery（重） | ★★ | ★★ |
| 学习/维护成本 | 低 | 中（本项目用不到其大头） | 低 | 最低但到顶了 |

**结论**：
- 主选 **FastAPI 0.11x + SQLAlchemy 2.x + Alembic + APScheduler + Pydantic v2**。决定性理由有二：① Pydantic 能把"量纲铁律"变成**构造期类型错误**（字段 `iv` 必须是小数 0.273，`iv_pct` 才是百分数，写反直接 422）；② OpenAPI 自动生成前端 TS 类型，前后端契约零漂移。
- **何时改选 Django**：若未来变成多用户产品（注册/权限/内容管理/后台审核），领域包 `vol.*` 原样搬进 Django 的 `services/` 层即可——这正是领域层不碰 web 框架的回报。
- Streamlit 不废弃：降级为**数据调试面板**（`app_debug.py`），正式用户界面走 Vue。

### 2.2 前端：**Vue 3 + Vite + TypeScript + Element Plus + ECharts**

- **Vue3 + Vite**：热更新快、单文件组件、国内资料最多。
- **ECharts（不是 plotly.js）**：金融图表生态最好——K 线、dataZoom、markArea 分位带、红涨绿跌主题一行配置；demo 的 plotly 报告保留为离线产物，不搬进前端。
- **Element Plus**：表格/表单/弹窗齐全，持仓管理和风控台主要是表格交互。
- **Pinia** 状态管理 + **axios** 实例封装。
- TS 类型从 `/openapi.json` 用 `openapi-typescript` 生成，**接口改动前端编译期报错**。

### 2.3 图表颜色与数字规范（写进前端常量，全站唯一）

- 红涨绿跌：`UP_COLOR=#e04343`、`DOWN_COLOR=#1faf6a`（中国惯例）。
- IV 一律显示百分数一位小数（27.3%），但**传输一律小数**（0.273）；盈亏显示 ¥，偏离显示 bp；图表 tooltip 必须带数据基准日期。

## 4. 核心类设计（签名级）

> 写法约定：领域类**不持有 IO 资源**（session/连接由调用方传入或以 DataFrame 进出）；docstring 第一行标注量纲；所有日期参数用 `date` 对象或 ISO 字符串。

### 4.1 配置与量纲（`config.py` / `units.py` / `contracts.py`）

### 4.5 风控层（`vol/risk/`）

```python
class Verdict(Enum): PASS / TRIM / REJECT

@dataclass
class RuleResult:
    rule_id: str; verdict: Verdict; detail: str
    allowed_qty: int | None        # TRIM 时给出削减后张数

class RiskRule(ABC):
    rule_id: str
    @abstractmethod
    def check(self, portfolio, proposed: ProposedTrade, mkt: MarketContext) -> RuleResult: ...

# 7 条实现（顺序即执行顺序）：
class VegaExposureRule(RiskRule): ...        # |组合Vega+新仓Vega| ≤ vega_limit → 超则 TRIM
class DeltaExposureRule(RiskRule): ...
class SingleStrikeRule(RiskRule): ...        # 同一行权价张数上限
class LiquidityGateRule(RiskRule): ...       # 流动性分 < liq_min_score → REJECT 开新仓
class DeepMoneyRule(RiskRule): ...           # |Δ|>0.85 或 <0.15 禁开新仓（只准平仓）
class CapitalUsageRule(RiskRule): ...
class SignalConsistencyRule(RiskRule): ...   # 建议方向必须与当日信号一致

class RiskChain:
    """逐级收窄：任一 REJECT → 整单拒；TRIM 传递削减后数量进入下一条。"""
    def __init__(self, rules: list[RiskRule]): ...
    def evaluate(self, portfolio, proposed, mkt) -> RiskVerdict: ...
    # RiskVerdict: approved: bool, final_qty, trace: list[RuleResult]（前端风控台直接渲染 trace）

class LiquidityScorer:
    """0-100 分 = 价差分(60%) + 成交量分(40%)，实时报价来自 OptionQuoteFetcher。"""
```

## 5. 数据库设计（SQLAlchemy 模型）

> SQLite 起步，字段类型避开 SQLite 特有写法，PostgreSQL 可平迁。Alembic 管迁移。

| 表 | 关键字段 | 说明 |
|---|---|---|
| `daily_metric` | `date PK, spot, atm_iv, iv_pct_40, iv_pct_120, curve_model, curve_r2, skew_25d, term_slope, vrp, momentum_20d` | 每日一张"市场体检表"，类比引擎的特征表 |
| `signal` | `id PK, date, engine, signal, confidence, valid_until, detail_json, created_at` | 索引 `(date, engine)`；valid_until=T+1（铁律8） |
| `advice_card` | `id PK, signal_id FK, verdict_json, card_json, created_at` | 建议卡片原样存档（审计追溯） |
| `position` | `id PK, code, qty, open_date, open_px, close_date, close_px, status, note` | 模拟持仓账本 |
| `position_snapshot` | `id PK, date, position_id FK, mv, delta, vega, theta, iv, spot` | 每日估值快照（归因输入） |
| `review_log` | `id PK, week, sample_n, hit_rate, baseline, by_regime_json, warn` | 周度复核记录 |
| `pipeline_run` | `id PK, started_at, finished_at, status, error, rows_fetched` | 管线运行记录（可观测性 + 防重入判断） |

设计要点：
- **快照表是归因的唯一输入**——归因只做"相邻两行快照的差分"，任何"累计值直接拆解"都在代码层禁止（check-risk-pnl 口径铁律的落地）。
- `pipeline_run` 存在的意义：`POST /api/jobs/refresh` 与定时任务共用一把"运行中"锁（查此表 status=running 即拒绝），UI 显示最近一次成功运行时间。
- JSON 字段（detail_json/card_json）只做展示透传，**不参与查询**；需要查询的指标一律提列。

### 6.2 契约规范

- 统一响应包：`{"code": 0, "data": {...}, "msg": "ok"}`；错误 `code!=0` + 人话 msg。
- **量纲写进字段名**：`iv`（小数 0.273）与 `iv_pct`（54.2）不允许混用；Pydantic 模型加 `Field(ge=0, le=1)` 物理约束，前端拿到即类型安全。
- 鉴权：`X-API-Key` 头（key 放 config.yaml），中间件统一校验；本地默认关闭，暴露到局域网时打开。
- 时间语义：所有日期参数/返回一律 `YYYY-MM-DD`（交易日），交易时段字段用 epoch 秒。
- OpenAPI 在 `/docs` 自动可见；前端 CI 用 `openapi-typescript src/api/schema.d.ts --output` 同步类型。

## 8. 调度与部署

### 8.1 调度（`jobs/scheduler.py`）

```python
scheduler = BlockingScheduler(timezone="Asia/Shanghai")
scheduler.add_job(daily_pipeline.run, "cron", day_of_week="mon-fri", hour=15, minute=35,
                  id="daily_pipeline", misfire_grace_time=3600, coalesce=True)
scheduler.add_job(weekly_review.run, "cron", day_of_week="mon", hour=8, minute=0, id="weekly")
# daily_pipeline.run 内部第一步: 检查 pipeline_run 是否有 running 记录 → 有则直接退出（双保险防重入）
```

Windows 本机形态：`schtasks /create /tn vol_scheduler /tr "<venv python> jobs/scheduler.py" /sc onlogon`（或沿用 daily_job 的 schtasks 方案，文件头注释已带命令）。管线幂等：同一天重跑 = 覆盖当日 metric/signal/snapshot（upsert by date）。

### 8.2 部署形态

- **形态 A（默认，Windows 本机）**：`uvicorn`（8000 端口）+ schtasks 定时器；前端 `npm run build` 产物拷入 `backend/static/`。
- **形态 B（迁云）**：`docker-compose.yml` 三服务：`api`（含静态托管）、`scheduler`（同一镜像不同 command）、`nginx`（可选，静态+反代）；SQLite 挂 volume，换 PostgreSQL 只改 `db/session.py` 连接串。
- 数据备份：`vol.db` + `data/cache/` 每日管线结束后 zip 到 `backups/YYYYMMDD/`（保留 30 份）。

## 11. 执行建议设计（借鉴 orange_zone：order-book-hft / pos-data）

> 回答"没有下单按钮，怎么给出下单建议"：系统不连券商通道，但把**执行所需的全部决策信息**算给用户，人是执行器。

### 11.1 挂单价三档（源自 order-book-hft.md 的被动/主动单概念）

`AdviceCardBuilder` 为每条腿输出三档参考价（实时盘口来自 `OptionQuoteFetcher`）：

| 档位 | 挂单价 | 适用 | 成本特征 |
|---|---|---|---|
| 激进（吃单） | 对手价：买入挂 ask₁ / 卖出挂 bid₁ | 信号刚翻转、怕错过 | 全额价差 |
| 稳健（中间价） | (bid₁+ask₁)/2 四舍五入到最小变动价位 | 默认推荐 | 约一半价差，大概率成交 |
| 保守（排队） | 本方价：买入挂 bid₁ / 卖出挂 ask₁ | 不急、IV 分位极端时可等 | 零价差，可能不成交 |

配套输出：当前价差（元与占比）、当日已成交量、以及"此合约 9:35–10:00 窗口内平均每分钟成交量"估计（用近 5 日分时成交量），供用户判断排队档是否来得及成交。挂单未成交的处理建议也写进卡片：**收摊前 14:50 撤单，未成交部分视为放弃，信号次日重算**。

### 11.2 持仓两源对账（源自 pos-data.md 的对账口径）

手动录入的持仓可能错，引入对账思想：

- **两源**：① 面板手动录入；② 券商对账单粘贴/导入（解析持仓表格）。
- **比对口径**（原样采用 pos-data.md）：逐合约 `总多头 / 总空头` 比对（all-match），或放宽为净持仓 `ttq = 多头 − 空头` 比对（net-match）；**不同合约不轧差**，跨合约敞口 = Σ|各合约净持仓|。
- 不一致时前端标红逐合约差异，**对账未通过的持仓不参与风控试算与归因**（垃圾进=垃圾出的闸门）。
- 对账结果落 `position_reconcile` 表（date, source, per_contract_json, status）。

### 11.3 执行质量回顾（源自 arb-latency.md 的事件时间线思想）

低频系统不需要微秒延迟分析，但借鉴其"事件时间线"记录：signal 发出时刻 → 用户标记"已执行"时刻（可选手动点）→ 成交回填价 vs 建议参考价的差 = **实现滑点**。累积统计展示"用户实际执行 vs 回测假设成本"的差距，让成本模型用真实数据迭代。落 `execution_log` 表（signal_id, acted_at, filled_px, slippage_bp）。
